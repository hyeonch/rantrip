# 랜덤 지하철 여행 앱 개발 기획서

## 현재 상태

`rantrip`은 랜덤 지하철 여행을 위한 모바일 중심 PWA다. MVP는 완료된 상태이며, 현재 앱은 출발역을 입력하면 랜덤으로 호선, 방향, 목적지를 뽑아준다.

이 문서는 MVP 이후 버전을 위한 개발 기획서다. 기존의 단순 랜덤 뽑기 앱에서, “뽑는 과정 자체가 재미있는 여행 기록 앱”으로 확장하는 것을 목표로 한다.

## 제품 방향

### 핵심 경험

사용자는 출발역만 입력한다. 앱은 슬롯머신처럼 호선과 방향을 뽑고, 지하철 노선도 위에서 목적지가 결정되는 과정을 보여준다. 여행 후에는 사진과 짧은 글을 남겨서, 매번의 랜덤 여행이 하나의 기록으로 쌓인다.

### 개발 방향

- 0차: TypeScript 전환으로 데이터/서비스 경계 준비
- 1차: 현재 MVP의 UX 버그 수정
- 2차: 랜덤 연출 중심 UI 개편
- 3차: 여행 기록 기능 추가
- 4차: 백엔드, 인증, 유저 데이터 확장

---

## 1. MVP 안정화

현재 구현은 기본 흐름은 완성되어 있으나, 입력과 결과 화면에서 몇 가지 UX 버그가 남아 있다.

### 수정할 버그

- 자동완성 첫 항목이 하이라이트된 상태에서 Enter를 누르면 해당 역이 선택되어야 한다.
- 검색 결과가 없는 상태에서는 Enter 또는 뽑기 버튼을 눌러도 진행되지 않아야 한다.
- 검색 결과가 없는 상태에서 진행 시도 시 입력창 shake 피드백을 준다.
- 최종 목적지가 뜬 뒤 결과 카드가 불필요하게 4개처럼 보이는 문제를 정리한다.
- 랜덤을 시작한 뒤 화면 상단에 출발역이 자연스럽게 보이도록 레이아웃을 조정한다.
- 최대 정거장 수 안내는 뽑힌 방향 기준의 개수만 보여준다.

### 완료 기준

- 잘못된 역 입력으로는 랜덤 뽑기가 시작되지 않는다.
- 키보드만으로 출발역 검색, 선택, 랜덤 시작이 가능하다.
- 목적지 공개 전후 화면 구조가 명확히 분리된다.

## 2. UI 개편

MVP UI는 기능을 순차적으로 보여주는 카드형 구조다. 다음 버전에서는 “랜덤이 발동되는 순간”을 앱의 가장 중요한 장면으로 만든다.

### 2-1. 전체 화면 흐름

```text
출발역 입력
  ↓
랜덤 시작
  ↓
호선 슬롯 연출
  ↓
상행/하행 슬롯 연출
  ↓
노선도 위 목적지 탐색 연출
  ↓
최종 목적지 + 노선도 표시
```

### 2-2. 호선 선택 연출

호선은 슬롯머신처럼 빠르게 돌아가다가 최종 호선에서 멈춘다.

요구사항:

- 후보 호선들이 세로 또는 원형 슬롯처럼 순환한다.
- 각 호선의 실제 노선 색상을 사용한다.
- 최종 호선이 멈출 때 색상, 진동감, 스케일 변화 등으로 확정감을 준다.
- 접근성을 위해 애니메이션 없이도 최종 결과 텍스트는 명확해야 한다.

### 2-3. 상행/하행 선택 연출

방향도 슬롯 형태로 보여준다.

요구사항:

- `상행`, `하행` 두 값이 빠르게 교차하다가 최종 방향에서 멈춘다.
- 방향 확정 후에는 현재 탑승역 기준으로 이동 가능한 정거장 수를 보여준다.
- 최대 정거장 수 입력은 방향 확정 이후에만 노출한다.

### 2-4. 목적지 선택 연출

최종 목적지는 단순 텍스트 공개가 아니라, 노선도 위에서 화살표가 왕복 이동하다가 멈추는 방식으로 보여준다.

요구사항:

- 선택된 호선의 역 목록을 간략 노선도로 렌더링한다.
- 탑승역, 후보 구간, 최종 목적지를 시각적으로 구분한다.
- 화살표 또는 현재 위치 마커가 후보 역들 사이를 왔다 갔다 한다.
- 최종 목적지에서 마커가 멈추고 목적지명이 크게 공개된다.
- 긴 노선은 모바일에서 가로 스크롤 또는 압축 렌더링을 고려한다.

### 2-5. 최종 목적지 화면

목적지 공개 화면에는 노선도를 함께 표시해서 “어느 방향으로 몇 정거장 갔는지”가 한눈에 보여야 한다.

표시 정보:

- 최종 목적지 역명
- 선택된 호선과 방향
- 실제 탑승역
- 출발 입력 역과 탑승역이 다를 경우 대체 탑승역 안내
- 탑승역부터 목적지까지의 구간 노선도
- 다시 뽑기 버튼
- 여행 기록 작성 버튼

## 3. 여행 기록 기능

랜덤 목적지에 도착한 뒤, 사용자가 그 여행을 사진과 짧은 글로 남길 수 있게 한다. 이 기능부터는 로컬 앱을 넘어 사용자 데이터 저장이 필요하다.

### 기본 기능

- 여행 기록 작성
- 사진 업로드
- 짧은 블로그 형태의 본문 작성
- 방문 날짜 자동 저장
- 출발역, 탑승역, 목적지, 호선, 방향 자동 저장
- 기록 목록 보기
- 기록 상세 보기

### 작성 화면

입력 항목:

- 제목
- 사진 1장 이상
- 짧은 본문
- 같이 간 사람 또는 태그
- 오늘의 한줄평

초기 버전에서는 과한 블로그 에디터보다, 모바일에서 빠르게 남길 수 있는 기록장에 가깝게 만든다.

### 기록 목록

목록에서는 여행이 쌓이는 느낌이 중요하다.

표시 정보:

- 대표 사진
- 목적지 역명
- 방문 날짜
- 호선 색상
- 짧은 본문 미리보기

## 4. 백엔드 확장

여행 기록 기능부터는 서버와 인증이 필요하다.

### 필요한 서버 기능

- 사용자 회원가입/로그인
- 세션 또는 토큰 기반 인증
- 여행 기록 CRUD
- 이미지 업로드 및 저장
- 사용자별 기록 조회
- 공개/비공개 기록 설정

### 데이터 모델 초안

```text
User
- id
- email
- displayName
- createdAt

Trip
- id
- userId
- departureName
- boardingName
- destinationName
- lineId
- lineName
- direction
- stopCount
- title
- body
- ratingText
- visibility
- visitedAt
- createdAt
- updatedAt

TripPhoto
- id
- tripId
- imageUrl
- sortOrder
- createdAt
```

### 백엔드 후보

초기 확장에서는 서버를 직접 크게 만들기보다 관리 비용이 낮은 선택지를 우선 검토한다.

- Supabase: 인증, DB, Storage를 빠르게 붙일 수 있음
- Firebase: 인증과 이미지 저장은 편하지만 관계형 조회는 다소 불편할 수 있음
- 직접 백엔드: 자유도는 높지만 운영 부담이 큼

현재 규모에서는 Supabase가 가장 현실적인 후보에 가깝다.

## 5. 기술 스택

### 현재

- React
- Vite
- JavaScript
- CSS
- PWA manifest
- 정적 `stations.json`

### 다음 단계 후보

- 언어: TypeScript로 전환
- 애니메이션: CSS animation 우선, 필요 시 Framer Motion 검토
- 노선도 렌더링: SVG 또는 HTML/CSS 기반 커스텀 렌더링
- 백엔드: Supabase 우선 검토
- 이미지 저장: Supabase Storage 또는 Firebase Storage
- 배포: Netlify 또는 Vercel

### TypeScript 전환 이유

Phase 5에서 인증, 여행 기록, 사진 업로드가 붙으면 `User`, `Trip`, `TripPhoto` 같은 데이터 모델이 앱 전체를 지나가게 된다. 이때 JavaScript만으로도 구현은 가능하지만, TypeScript를 먼저 도입하면 랜덤 결과, 기록 초안, 서버 저장 데이터의 모양을 더 안정적으로 맞출 수 있다.

전환은 기능 개발 전에 작게 끝낸다. 목표는 앱 구조를 크게 바꾸는 것이 아니라, 기존 React + Vite 프로젝트를 `.tsx/.ts` 기반으로 옮기고 빌드가 통과하는 상태를 만드는 것이다.

## 6. 개발 순서

### Phase 0. TypeScript 전환

- TypeScript 의존성 추가
- `tsconfig` 구성
- React 엔트리와 컴포넌트를 `.tsx`로 전환
- 유틸과 데이터 접근 코드를 `.ts`로 전환
- `Station`, `Line`, `Trip`, `TripPhoto` 타입 초안 작성
- 기존 기능이 동일하게 동작하는지 확인

### Phase 1. MVP 안정화

- 입력 자동완성 Enter 동작 수정
- 검색 결과 없음 상태 처리
- 결과 카드/출발역 레이아웃 수정
- 방향별 최대 정거장 표시 수정

### Phase 2. 랜덤 연출 UI

- 호선 슬롯 컴포넌트 구현
- 방향 슬롯 컴포넌트 구현
- 랜덤 진행 상태 모델 정리
- 기존 단계형 카드 UI를 연출형 화면으로 교체

### Phase 3. 노선도 목적지 연출

- 선택된 호선의 간략 노선도 렌더링
- 탑승역, 후보 구간, 목적지 강조
- 화살표 왕복 애니메이션 구현
- 최종 목적지 화면에 구간 노선도 추가

### Phase 4. 여행 기록 로컬 버전

- 기록 작성 UI 구현
- 사진 첨부 UI 구현
- 우선 localStorage 또는 IndexedDB로 임시 저장
- 기록 목록/상세 화면 구현

### Phase 5. 백엔드 도입

- 인증 도입
- Trip/TripPhoto 저장 구조 구현
- 이미지 업로드 연결
- 사용자별 기록 조회 구현
- 배포 환경 구성

## 7. 설계 메모

- 랜덤 뽑기 로직과 애니메이션 연출은 분리한다. 결과는 먼저 계산하되, UI는 계산된 결과를 향해 멈추는 방식으로 구현한다.
- 노선도 렌더링은 실제 지하철 지도처럼 복잡하게 시작하지 않는다. 먼저 “선형 노선도”로 구현하고, 필요할 때 지선/환승 표현을 확장한다.
- 여행 기록 기능은 백엔드부터 붙이기보다, 먼저 로컬 저장으로 UX를 검증한 뒤 서버 저장으로 옮기는 편이 낫다.
- 앱의 핵심 정서는 “목적지 추천”보다 “우연히 정해지는 여행의 설렘”에 둔다.
